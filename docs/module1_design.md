# 模組 1：動態時序戰情儀表板（Dynamic Time-Series Dashboard）

## 一、解題方向

大型活動期間，指揮官需要的不是單一時間點的快照，而是「事情是怎麼一路演變到現在的」——某路段的飽和度是從幾點開始爬升、某站點的人潮是不是持續加速成長。傳統作法是人工盯著即時數字，很難看出趨勢，也容易錯過「剛好跨過門檻」的那一刻。

因此本模組把 Dashboard 做成**可以在時間軸上前後拖動的動態戰情室**，而不是一個只顯示「現在」的靜態頁面：

- 時間軸滑桿（含播放／暫停／倍速），拖到任一時間點，全畫面（KPI、地圖、路段清單、基地台狀態）同步切換到那個時間點的狀態
- 針對第 1／3 條 SOP 門檻做**逐時間點比對**：不是「現在有沒有觸發」，而是「這個時間點是不是比上一個時間點『新』觸發的」，只在真正跨過門檻的那一刻產生預警，不會每個時間點都重複跳提示
- 點擊任一路段／站點，可以切換成該實體自己的歷史雙指標走勢圖（路段：飽和度＋車速；站點：人流＋成長率）

**刻意的範圍界線**：本模組只做「監測、判斷門檻、產生預警摘要」，**完全不產出調度／引導／分流等行動建議**——那是模組二（事件處置）的職責。這是這次開發過程中明確拿掉的部分：早期版本曾經在 SOP-3 觸發文字裡放「過站不停、調度接駁專車、引導至 OO 站」這類建議，後來確認這會跟模組二的職責重疊，全部移除，`TriggerDecision.actions` 固定回傳空陣列。

## 二、AI 技術應用

與模組三、五不同，模組一**沒有走 LLM 判斷 SOP 是否觸發**——門檻判斷（第 1／3 條）完全由 `thresholds.py` 的純函式計算完成，數字算完才交給 LLM。LLM 在這裡只有一個角色：**把已經算好的觸發結果，轉寫成一到兩句給第一線人員看的中文預警提示**，不重新計算、不質疑門檻。

| 項目 | 說明 |
|---|---|
| 模型 | Ollama 本機推論，`qwen2.5:1.5b`（`OLLAMA_MODEL` 環境變數可調） |
| 呼叫方式 | 直接用 stdlib `urllib` 打 `/api/generate`，沒有走額外的 LLM SDK／抽象層 |
| 觸發時機 | 只有「這個時間點比上一個時間點新觸發」的門檻才會呼叫 LLM；沒有新觸發時 `summary` 回傳空字串，不會每次都打一次 LLM |
| System Prompt 限制 | 明確要求「不要給出調度、派遣、引導路線或分流等行動建議，那是其他模組的職責，這裡只做狀態說明與預警提示」 |
| Fallback | Ollama 逾時（10 秒）或連線失敗時，自動退回規則式樣板文字（`【SOP 第 X 條 條款名】實體名：判斷依據。`），不會讓 API 掛掉，只是文字品質比較陽春 |

**跟模組三的差異**：模組三描述的 `warroom/llm/client.py` 統一 LLM 抽象層（可切 Bedrock / Ollama / Mock）目前**還沒有被模組一使用**——`llm_summary.py` 是獨立、寫死呼叫本機 Ollama 的簡單實作，沒有 `LLM_MODE` 切換機制。如果之後要接正式賽場的 Bedrock，這裡需要額外改接那層抽象層，目前還沒做。

## 三、數據資料應用

### 資料來源

- `city_traffic_flow.csv`：路段飽和度、平均車速 → SOP 第 1 條紅黃燈分級
- `signaling_crowd_density.csv`：站點人數、成長率 → SOP 第 3 條捷運分流門檻
- `road_network_geometry.json`：路段名稱、替代路線清單 → 觸發時附上替代道路名稱給 LLM 參考（**不**做路網重規劃，那是模組二的疏散路徑邏輯）
- `warroom/data_source/road_coords.json`（本模組新增，非官方原始資料）：地圖畫路線／站點標記用的經緯度座標。官方資料完全沒有座標欄位，這份是額外用 OpenStreetMap Overpass API 查真實道路描點產生的，跟業務資料分開存放

### 資料處理流程

```
CSV / JSON 原始資料
      ↓
data/snapshot.py 正規化（跟模組二、三共用同一層，確保數值一致）
      ↓
Traffic Snapshot
      ↓
thresholds.py 純函式門檻判斷（第 1／3 條）
      ↓
跟「上一個可用時間點」的判斷結果比對 → 找出「新觸發」項目
      ↓
新觸發項目才會被送進 LLM → 產生預警提示文字
      ↓
/api/dashboard 一次回傳：快照＋全部觸發清單＋新觸發清單＋預警摘要
```

跟模組二一樣，本模組**不自己重新解析 CSV／JSON**，一律透過 `data/snapshot.py`；跟模組三、五共用同一份 Traffic Snapshot，確保三個模組看到的數字不會兜不起來。

## 四、使用者流程

```
開啟 Dashboard（預設載入最新時間點）
      ↓
拖動時間軸滑桿 / 點播放鍵自動快轉
      ↓
每個時間點：KPI 條、地圖、路段清單、基地台狀態面板同步更新
      ↓
比對上一時間點，若有「新」跨過門檻的路段／站點
      ↓
右側預警卡片顯示（SOP-1 壅塞 / SOP-3 分流），LLM 生成一到兩句預警摘要
      ↓
點擊任一路段／站點清單項目
      ↓
地圖左下角彈出該實體的雙指標歷史走勢圖
      ↓
指揮官可持續拖動時間軸回顧任一時段的狀態
```

時間軸的資料同時驅動模組五的 SOP-6 卡片與基地台狀態面板——兩個模組共用同一個時間點，避免「時間軸調到 18:00，其他卡片卻還停在最新時間」的不一致（這是這次開發中修過的一個實際 bug）。

## 五、已知限制／開放問題

比照模組二「疑問」與「額外處理的東西」的做法，誠實列出目前還沒解決、之後可能需要處理的部分：

1. **SOP 第 3 條目前只判斷單一站點 `BS_MRT_BL17`**，寫死在 `thresholds.py`。如果比賽資料之後擴增其他捷運站也要套用同一條門檻，需要先決定規則範圍（例如所有 `BS_MRT_` 開頭都套用），這是業務邏輯決定，還沒有跟其他模組確認。

2. **時間軸快轉時沒有請求序號／abort 機制**：`loadSnapshotAt()` 每個 tick 平行打 3 支 API，播放速度快、又剛好某個時間點觸發 LLM 摘要（呼叫可能到 10 秒）時，較舊的回應有可能比較新的晚到，畫面可能短暫顯示不同步的資料。目前還沒修，是已知風險而非已修復項目。

3. **地圖座標是額外維護的資料，不是官方原始資料的一部分**：`road_coords.json` 需要人工執行 `scripts/fetch_road_coords.py` 才能在新增路段時補上，新站點更是完全需要手動補（OSM 上查不到自訂的基地台位置）。

4. **沒有走模組三描述的統一 LLM 抽象層**，`LLM_MODE=bedrock/ollama/mock` 目前只對模組三有效，模組一是獨立的 Ollama-only 實作，正式賽場如果要換成 Bedrock，這裡需要額外改。

5. **資料快取沒有熱重載**：`data/snapshot.py` 用 `@lru_cache(maxsize=1)` 快取整份原始檔，比賽現場若需要替換資料檔案，需要重啟 server 才會生效。
